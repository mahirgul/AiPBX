Engineering Deep Dive

Architectural Rationale: Why & How We Built It

Every engineering decision in AiPBX was made to resolve real-world pain points found in traditional PBX systems: restrictive firewalls, split identities, bloated dependencies, and security vulnerabilities.

1

Why Port 443 ALPN Multiplexing?

⚠ The Challenge
Enterprise, university, and hotel firewalls block non-standard ports (5060 SIP, 8088 WS, 3478/5349 TURN). Remote workers and mobile users fail to establish WebRTC media behind these strict NATs.
💡 Our Architectural Solution
Nginx operates at L4 using ssl_preread on on Port 443. It inspects the TLS ClientHello ALPN string without decrypting: connections with ALPN (h2, http/1.1) go to Apache (8443); non-ALPN traffic goes to Coturn (5349).
🚀 Real-World Impact
Web portal, mobile API, WebSocket signaling, and WebRTC TURNS media relay all share standard Port 443 without certificate duplication. 100% firewall traversal!
2

Why Dedicated Port 80 for ACME?

⚠ The Challenge
Let's Encrypt / Certbot renewal bots do NOT send ALPN extensions. If Port 80 unconditionally redirected ACME challenges to Port 443, Nginx would route them to Coturn, causing automated SSL renewals to permanently fail.
💡 Our Architectural Solution
Apache owns Port 80 directly. It serves /.well-known/acme-challenge/ locally without redirection, while permanently 301-redirecting all standard browsing traffic to HTTPS.
🚀 Real-World Impact
Automated zero-touch Let's Encrypt certificate issuance and quarterly renewals execute seamlessly without manual administrator intervention.
3

Why Dual-Endpoint Architecture?

⚠ The Challenge
Traditional PBXs require separate extension numbers for desk phones (e.g. 1001) and softphones/mobile apps (e.g. 2001). This breaks call transfers, fragments CDR reporting, and confuses callers.
💡 Our Architectural Solution
A single extension (e.g. 1000) controls dual PJSIP endpoints: 1000-sip (hardware desk phone via UDP/TCP 5060) and 1000-mob-webrtc (Android & web softphone via WSS).
🚀 Real-World Impact
Both endpoints ring simultaneously. If answered on mobile, the desk phone silences. Outbound calls show the exact same caller ID and CDR history is unified.
4

Why Standalone Go Chat Service?

⚠ The Challenge
PHP is stateless and request-driven. Maintaining persistent WebSocket connections in PHP exhausts server memory, introduces process locking, and scales poorly with concurrent chat users.
💡 Our Architectural Solution
Built an independent Go microservice with Gorilla WebSocket on Port 8086. It compiles to a self-contained static binary (CGO_ENABLED=0) requiring under 20MB RAM.
🚀 Real-World Impact
Supports thousands of concurrent connections with native Goroutines. Provides instant message delivery, typing indicators, read receipts, and file transfers with negligible CPU footprint.
5

Why Native Kotlin + Headless WebRTC?

⚠ The Challenge
Third-party Android native SIP SDKs (PJSIP C-wrappers, Linphone) bloat APKs to 40MB+, crash unpredictably across Android 12-16 vendor skins, and struggle with background Doze mode.
💡 Our Architectural Solution
Kotlin manages Android system integration (Foreground Service, Telecom, FCM wake-up, UI, SQLite, Chat, Logs), while a headless WebView executes a standard WebRTC engine (phone_engine.html).
🚀 Real-World Impact
Featherweight 2.8 MB APK, 100% standards-compliant WebRTC Opus audio, zero native library crashes, and instantaneous incoming call wake-up even when the phone is asleep.
6

Why Two-Tier MariaDB Privileges?

⚠ The Challenge
Most web portals use a single database account with full DDL rights. If an SQL injection exploit occurs, attackers can execute DROP TABLE or alter critical PBX configuration tables.
💡 Our Architectural Solution
Two separate database users: aipbx_portal only has DML rights (SELECT, INSERT, UPDATE, DELETE), while aipbx_migrator is used solely for DDL migrations.
🚀 Real-World Impact
Even in worst-case application flaws, attackers cannot destroy schema structures or grant themselves elevated privileges.

Mobile Companion

Native Android App for Enterprise PBX

AiPBX includes a first-class native Android application written in Kotlin. It transforms any smartphone into an enterprise extension with zero complex configurations.

  • ⚡
    Instant FCM Background Wake-Up Incoming calls trigger high-priority push notifications, waking the device from deep sleep with a native ringer.
  • 💬
    Built-in Team Chat Tab Real-time instant messaging powered by Go WebSockets with typing indicators and image attachments.
  • 🔄
    Live Call Forwarding (CFU / CFB / CFNR) Adjust call forward rules (Always, Busy, No-Answer) directly from the mobile settings in real time.
  • 📑
    In-App Diagnostics Log Viewer Engineers can view, filter, and export full SIP, WebRTC, and HTTP network logs directly from the device.
