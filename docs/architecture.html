🏗️ Sistem Mimarisi & Mühendislik Rasyoneli

2. Neden Port 443 ALPN Stream Çoklama?

Geleneksel VoIP santral kurulumlarında SIP sinyalleşmesi için UDP 5060, WebRTC WSS için 8089, STUN/TURN için 3478 veya 5349 gibi çok sayıda harici port açılması zorunludur. Ancak bankalar, hastaneler, üniversiteler ve kurumsal plaza ağları Port 80 ve 443 dışındaki tüm giden portları katı güvenlik duvarları (Firewall) ile bloke eder.

💡
AiPBX Çözümü: Nginx Layer 4 (L4) Stream modülü ve ssl_preread on direktifi sayesinde, TLS el sıkışmasındaki (ClientHello) Application-Layer Protocol Negotiation (ALPN) baytlarını inceler. SSL sertifikasını çözmeden şifreli trafiği alt servislere dağıtır.

Nginx L4 Stream Yapılandırması:

/etc/nginx/nginx.conf (L4 Stream Bloğu) 
stream {
    map $ssl_preread_alpn_protocols $upstream_backend {
        # Standart web tarayıcılar, mobil REST API çağrıları
        "~*http"        apache_https;
        "~*h2"          apache_https;
        
        # WebRTC TURNS medya trafiği (ALPN göndermez)
        default         coturn_turns;
    }

    upstream apache_https {
        server 127.0.0.1:8443;
    }

    upstream coturn_turns {
        server 127.0.0.1:5349;
    }

    server {
        listen 443;
        proxy_pass $upstream_backend;
        ssl_preread on;
        proxy_connect_timeout 5s;
        proxy_timeout 3600s;
    }
}

Bu sayede kullanıcı ister mobil veri (4G/5G) üzerinden, ister en sıkı kurumsal Wi-Fi ağından bağlansın; ek hiçbir VPN kurmadan tek bir https://santral.sirket.com adresi üzerinden hem web paneline girer, hem sesli görüşme yapar, hem de sohbet eder.

3. Dual-Endpoint PJSIP ve WebRTC Mimarisi

Piyasadaki birçok hazır PBX dağıtımı (FreePBX, Issabel vb.) tek bir dahili için aynı anda hem donanımsal masa telefonunu hem de WebRTC tarayıcıyı bağlamakta zorlanır. NAT arkasındaki masa telefonu ile WebRTC'nin şifreleme ve medya taşıma gereksinimleri taban tabana zıttır:

  • WebRTC (Tarayıcı & Mobil): WSS taşıyıcı, DTLS-SRTP şifreleme, ICE adayları, AVPF profil ve Opus ses kodeği gerektirir.
  • Masa Telefonu (IP Phone / ATA): UDP veya TLS taşıyıcı, SDES-SRTP veya şifresiz RTP, SAVP/RTP profil ve G.711u/a kodeği kullanır.

AiPBX bu sorunu Dual-Endpoint Eşlemesi ile çözer. Dahili 1000 oluşturulduğunda sistem veritabanında iki ayrı PJSIP profili açar:

Endpoint ID Kullanım Amacı Taşıyıcı & Port Şifreleme & Kodek
1000 Donanım IP Telefon / Masaüstü SIP UDP / TLS (Port 5060/5061) SDES-SRTP / G.711a, G.722, G.729
1000-webrtc Web Tarayıcı & Native Mobil İstemci WSS (Port 443 ALPN / 8089) DTLS-SRTP + ICE / Opus (HD Ses)
📞
Çatal Zil (Forked Ringing): Dışarıdan 1000 nolu dahili arandığında Asterisk dialplanı Dial(PJSIP/1000&PJSIP/1000-webrtc,30) komutuyla hem kullanıcının masasındaki IP telefonu hem de cebindeki mobil uygulamayı aynı anda çaldırır. İlk cevaplanan cihaz çağrıyı alır, diğeri sessizce kapanır.

4. Neden Bağımsız Go Real-Time WebSocket Servisi?

PHP; kısa ömürlü HTTP istek-yanıt (Request-Response) yaşam döngüsü için mükemmel ve kararlıdır, ancak on binlerce eşzamanlı istemcinin açık tuttuğu uzun süreli (persistent) WebSocket bağlantılarını yönetmek için optimize edilmemiştir. Node.js ise ek JavaScript çalıştırma ortamı ve bellek maliyeti getirir.

AiPBX, santral içi bireysel ve çok katılımcılı grup sohbet motorunu saf Go (Golang) ile geliştirmiştir (/opt/aipbx/bin/aipbx-chat):

  • Mikro Bellek Ayak İzi: 10.000 aktif eşzamanlı WebSocket istemcisi yalnızca ~28 MB RAM tüketir.
  • Goroutine Tabanlı Eşzamanlılık: Her bağlantı için ağır işletim sistemi iş parçacığı yerine hafif Go kanalları kullanılır.
  • Sıfır Dış Bağımlılık: Tek bir statik ikili dosya (binary) olarak derlenir, sunucuda ek paket veya framework kurulumu gerektirmez.
  • Anlık Varlık (Presence) ve Yazıyor Bildirimi: Kullanıcının çevrimiçi durumu, okundu bilgisi ve grup mesajları milisaniye mertebesinde dağıtılır.

5. Asterisk Yapılandırma Senkronizasyon Döngüsü

AiPBX'te Asterisk yapılandırma dosyaları asla elle düzenlenmez. Veritabanı (MariaDB), sistemin tek ve mutlak gerçeklik kaynağıdır (Single Source of Truth). Bir ayar değiştirildiğinde aşağıdaki atomik döngü işletilir:

Yapılandırma & Otomatik Geri Alma (Rollback) Akışı 
Web UI / REST API İstek
        │
        ▼
Controller Yetki ve Doğrulama
        │
        ▼
Service Veritabanına Yazar (MariaDB DML)
        │
        ▼
Sync Generator (src/sync/*.php)
        ├── 1. Mevcut .conf dosyasının .bak yedeğini alır
        ├── 2. DB'den son güncel veriyi sorgular ve /etc/asterisk/pbx/*.conf dosyasına yazar
        └── 3. Asterisk'e yeniden yükleme komutu gönderir (dialplan reload, queue reload...)
                │
                ├── [ BAŞARILI ] ──► Audit log kaydı düşülür, .bak dosyası temizlenir.
                └── [ HATA ]     ──► OTOMATİK ROLLBACK: Eski .bak anında geri yüklenir,
                                     servis kesintisi %100 önlenir ve hata loglanır.
